# M1 clean profile, 2026-11-23

Metric: **bridge decode → consumer** (see the [README](README.md)). It excludes
the vehicle and link side. Gate: overall p99 ≤ 100 ms on this loopback segment,
a smoke gate that catches gross regressions in the bridge and DDS. It is not
the end-to-end telemetry target of design §10, which needs the vehicle-side
method that arrives in M4. Result: pass.

## Setup

- Scenario: `bench/scenarios/m1-clean.env`: four PX4 SIH vehicles, no link
  impairment, bridge and probe on one host over loopback DDS.
- Pose published at a nominal 20 Hz per vehicle; 60 s recorded.
- Built with the `dev` preset. Check out commit `5448243b0406c2b243576d29a0838a9861fcd070`
  and run `bench/run.sh m1-clean` to reproduce; the run was made from a clean
  tree at exactly that commit.
- Cyclone DDS 11.1.0, cyclonedds-cxx 11.1.0.

The raw output of this run is in [2026-11-23-m1-clean/](2026-11-23-m1-clean/),
exactly as `bench/run.sh` wrote it: [pose.csv](2026-11-23-m1-clean/pose.csv)
(one row per received sample), [report.md](2026-11-23-m1-clean/report.md),
[host.txt](2026-11-23-m1-clean/host.txt) and
[bridge.log](2026-11-23-m1-clean/bridge.log). The report can be rebuilt from
the CSV:

```sh
python3 bench/report/latency.py --gate-p99-ms 100 docs/benchmarks/2026-11-23-m1-clean/pose.csv
```

Each vehicle delivered about 19.4 samples/s over the 60 s, a little under the
nominal 20 Hz. There are no gaps between the first and last received sample of
each vehicle. The seq-gap column counts drops the probe saw, so anything lost
before the probe subscribed or after it stopped is not visible in it. This is one
60 s run on one machine with nothing else loaded; it shows the order of
magnitude, not a distribution across runs.
