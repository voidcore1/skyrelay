# Claiming the Unowned MAVLink-to-DDS Middle Ground

As of November 2026, **no maintained open-source project does what this one proposes**: a ROS-free, autopilot-agnostic gateway that decodes MAVLink from both PX4 and ArduPilot into a curated, versioned DDS data model, built for several vehicles at once and secure by default. Every maintained DDS route to a drone belongs to one autopilot and exposes that autopilot's internal messages (PX4's uXRCE-DDS and experimental Zenoh paths, ArduPilot's AP_DDS), while the autopilot-agnostic tools require ROS (MAVROS), speak gRPC with a server reported to handle one vehicle (MAVSDK), or forward untyped frames (routers), and the newer browser ground stations connect straight to MAVLink over WebSockets. The project should therefore not try to win on ground-station features, where a GPL-3.0 web station already offers fleet boards, MAVLink signing and a video relay; it can win on a published IDL, fault isolation between vehicles, DDS-Security plus MAVLink 2 signing switched on from the start, a reproducible fault-injection benchmark that publishes latency percentiles, joint MAVLink-and-DDS recording with deterministic replay, and a small, permissively licensed C++ MISB ST 0601 encoder fed from the same DDS bus. The planned tooling largely holds up: Cyclone DDS/cyclonedds-cxx 11.1.0, pinned MAVLink C headers, PX4 v1.17.0 and ArduPilot Copter 4.7.x SITL on Gazebo Harmonic, MediaMTX 1.21.4 with GStreamer 1.28, and MapLibre GL JS 6 with PMTiles. The sharpest pitfalls are that the simulation stack does not support Ubuntu 26.04 (run it in 24.04 containers), PX4 v1.18 (now at rc2) changes signing and DDS namespaces, no public evidence shows Cyclone completing a secure handshake with another vendor's DDS, KLV metadata paths through GStreamer and FFmpeg have broken silently between versions, and the 5-second lost-link target is almost used up by MAVLink's conventional heartbeat-loss rule unless the bridge detects outages from its high-rate telemetry instead.

## No maintained gateway puts both autopilots on a neutral DDS bus

Each maintained route from a drone into DDS belongs to one autopilot and speaks that autopilot's internal dialect. PX4's uXRCE-DDS runs a Micro XRCE-DDS client inside the flight stack and an agent on the companion computer; the exported topic set is **fixed at build time** by `dds_topics.yaml`, and messages are generated from PX4's internal uORB definitions ([PX4 docs: uXRCE-DDS](https://docs.px4.io/main/en/middleware/uxrce_dds)). Those `px4_msgs` types are branched per PX4 release (latest 1.17.0, March 2026), and although a translation node has bridged versioned messages since v1.16, unversioned messages must still match exactly ([PX4/px4_msgs](https://github.com/PX4/px4_msgs); [PX4 docs: message translation node](https://docs.px4.io/main/en/ros2/px4_ros2_msg_translation_node)). PX4 publishes with best-effort, transient-local QoS that does not match ROS 2's reliable defaults, and its docs state that the DDS transport is **"unauthenticated and reaches uORB directly"**, with security "up to the integrator" ([PX4 docs: uXRCE-DDS](https://docs.px4.io/main/en/middleware/uxrce_dds)). The experimental Zenoh path carries the same warning, needs a reboot to change topic mappings ([PX4 docs: Zenoh](https://docs.px4.io/main/en/middleware/zenoh)), and does not yet support more than one SITL instance ([PX4 pre-built SITL packages](https://docs.px4.io/main/en/simulation/px4_sitl_prebuilt_packages)). ArduPilot's AP_DDS exposes its own `ap/*` topics and `ardupilot_msgs` types, supports only ROS 2 Humble, and is binary-stable only within one ArduPilot minor release ([ArduPilot: ROS 2 interfaces](https://ardupilot.org/dev/docs/ros2-interfaces.html)); two vehicles collided on the same `/ap` node until **PR #32510 added opt-in per-system-ID namespaces on 25 March 2026** ([ArduPilot PR #32510](https://github.com/ArduPilot/ardupilot/pull/32510)), a change whose presence in a stable release is unverified.

The autopilot-agnostic tools each stop short in a different direction. MAVROS turns any MAVLink autopilot into ROS 2 topics and services across Humble to Rolling, but it requires ROS, publishes ROS message types rather than a curated model, does not document multi-vehicle namespacing, and even its current version differs between sources (2.16.0 in the ROS index changelog dated 27 September 2026, 2.15.0 on the repository summary) ([mavlink/mavros](https://github.com/mavlink/mavros); [ROS index](https://index.ros.org/p/mavros/)). MAVSDK reached **v4.2.1 on 17 November 2026** and gained MAVLink 2 signing only in v4.2.0, but its gRPC `mavsdk_server` has been described as limited to one vehicle per server and does not expose signing ([MAVSDK releases](https://github.com/mavlink/MAVSDK/releases); [PX4 forum](https://discuss.px4.io/t/please-help-me-understand-mavsdk-server/48103); [MAVSDK PR #3198](https://github.com/mavlink/MAVSDK/pull/3198)). Routers move frames without a data model: mavlink-router is Apache-2.0 with a last tag of v4 in February 2024 and commits continuing into 2026, and Blue Robotics' Rust mavlink-server adds Zenoh, WebSocket and REST endpoints ([mavlink-router](https://github.com/mavlink-router/mavlink-router); [bluerobotics/mavlink-server](https://github.com/bluerobotics/mavlink-server)). The closest design analogue is **mavlink2grpc (December 2025), which auto-generates protobuf definitions from the MAVLink XML**; in that thread a MAVSDK maintainer called MAVSDK's own direct-MAVLink path "less strongly typed" JSON ([PX4 forum: mavlink2grpc](https://discuss.px4.io/t/project-mavlink-grpc-bridge-seeking-feedback/48119)). It targets gRPC and mirrors MAVLink message for message instead of offering a domain model. A Zenoh MAVLink plugin exists only as a 6-commit prototype ([roby2014/zenoh-plugin-mavlink](https://github.com/roby2014/zenoh-plugin-mavlink)), and the 2026 aerial-autonomy-stack paper describes a common ROS 2 interface over PX4 and ArduPilot without saying which bridge it uses ([arXiv 2602.07264](https://arxiv.org/abs/2602.07264)).

|---|---|---|---|---|---|

| PX4 Zenoh node | PX4 only | uORB via rmw_zenoh | Multiple instances not yet supported | Unauthenticated | Experimental |

No standard data model fills the gap either. ROS's aerial interface standard, REP-147, is **Deferred**, and a newer proposal for autopilot-agnostic ROS messages aligned with MAVLink's common set shows no sign of adoption ([REP-147](https://reps.openrobotics.org/rep-0147/); [ROS Discourse proposal](https://discourse.openrobotics.org/t/new-rep-to-replace-rep-147-for-autopilot-agnostic-ros-messages-optimized-for-flight-stacks/36362)); ArduPilot developers call their own bridge interim until standard aerial messages exist ([ArduPilot forum](https://discuss.ardupilot.org/t/offboard-terrain-navigation-for-plane-with-ros-2-ap-dds/114418)). Open-source tooling for formal unmanned-systems standards is no better, with JAUS SDKs commercially dual-licensed and the open bridges dating from ROS 1 or early ROS 2 ([OpenJAUS SDK](https://openjaus.com/sdk); [fkie/iop_core](https://github.com/fkie/iop_core)), and this research found no permissively licensed, maintained DDS/IDL model for aerial vehicles. MAVLink's common message set is therefore the de facto neutral vocabulary, and the project's IDL should be **a curated, versioned projection of MAVLink common semantics** (vehicle state, health, link quality, the command request/acknowledgement lifecycle, missions, video metadata) rather than a new ontology. Staying close to MAVLink keeps mapping tables honest, matches the direction the ROS proposal was taking, and limits the risk of being orphaned if a standard aerial ROS model finally arrives.

The strongest case against building at all is that MAVROS on ROS 2 Lyrical, over a DDS middleware, already puts PX4 and ArduPilot on DDS. For ROS users it does. But it forces ROS on every consumer, yields `mavros_msgs` rather than a stable model that a non-ROS DDS system can subscribe to, and ships no security or per-vehicle isolation by default. The project should neutralise this argument by offering an optional ROS 2 mirror of its topics, not by competing with MAVROS.

### Fleet ground stations stop at dashboards over N MAVLink links

The mature ground control stations are single-operator desktop tools with multi-vehicle support added later. QGroundControl's latest stable release is v5.1.5 (1 October 2026), with multi-vehicle support dating from v5.0 ([QGC releases](https://github.com/mavlink/qgroundcontrol/releases); [QGC v5.1 What's New](https://docs.qgroundcontrol.com/Stable_V5.1/en/qgc-user-guide/getting_started/whats_new.html)), and anecdotal forum reports describe connect/disconnect flicker beyond three vehicles and repeated lost command acknowledgements in a 10-vehicle PX4 SITL ([PX4 forum: flicker](https://discuss.px4.io/t/qgc-multi-vehicle-connect-disconnect-flicker-3-drones-com-dll-except-com-dl-loss-t-questions/47112); [PX4 forum: 10 drones](https://discuss.px4.io/t/10-drones-in-px4-sitl-gazebo/48385)). Mission Planner's swarming is leader–follower only, needs a radio link per vehicle, and calls itself an "experimental beta" ([ArduPilot Mission Planner: Swarming](https://ardupilot.org/planner/docs/swarming.html)).

The browser wave is more modern but still connects straight to MAVLink. **ADOS Mission Control is the closest overlap with this project**: Next.js 16 and React 19 with CesiumJS, MAVLink over WebSocket and WebSerial, MQTT-backed fleet dashboards with bulk and formation actions, MAVLink 2 signing with a non-extractable Web Crypto key, an RTSP-to-WebSocket video relay, self-hostable offline operation, and a **GPL-3.0-only** licence ([altnautica/ADOSMissionControl](https://github.com/altnautica/ADOSMissionControl)). Argus supports ArduPilot only and is maintenance-only ([L-X-Yao/argus](https://github.com/L-X-Yao/argus)), and Cockpit's missions are limited to basic waypoints and surveys ([Blue Robotics forum](https://discuss.bluerobotics.com/t/cockpit-1-0-0-release/17744)). Frameworks for several drones solve a different problem: Aerostack2 (BSD-3) provides ROS 2 namespacing and coordination for multi-drone autonomy but is not an operator station ([aerostack2](https://github.com/aerostack2/aerostack2)), and Skybrush is GPL-3.0 and built for light shows ([skybrush-io](https://github.com/skybrush-io)). None of these uses DDS, publishes a typed data model that other programs can subscribe to, or publishes latency measurements, and none documents failure isolation between vehicles or per-vehicle command queues with explicit acknowledgement and timeout semantics. The web control station should therefore be **a reference consumer of the DDS bus**, with a minimal fleet view and an independent command panel per vehicle that makes acknowledgement state visible, rather than a rival on mission-planning breadth.

## Measured, fault-injected latency is the least contested ground

Published latency numbers are scattered, and none matches this project's budget. The most rigorous autopilot-to-companion study (PX4 v1.14 on a Pixhawk 4, a Raspberry Pi 4, UART at 921600 baud) measured one-way latency of **1.3–1.8 ms for XRCE-DDS against 1.7–2.1 ms for MAVLink/MAVROS** ([Sensors 2023, PMC10674650](https://pmc.ncbi.nlm.nih.gov/articles/PMC10674650/)). Over real networks, Cyclone DDS performed best on Ethernet and **Zenoh best on Wi-Fi and 4G** ([arXiv 2309.07496](https://arxiv.org/abs/2309.07496)), and in a multi-robot mesh study Fast DDS showed **delays of up to ~50 s on an unstable network**, with the authors noting that prior work has almost no quantitative wireless data ([arXiv 2407.03091](https://arxiv.org/pdf/2407.03091)). A 4G LTE control-link study measured a 97 ms mean (17.4 ms standard deviation) ([Drones 2025](https://doi.org/10.3390/drones9120812)), and a 2026 paper on MAVLink telemetry over LTE states that it did not measure end-to-end latency at all ([MDPI Eng. Proc. 158/1/30](https://www.mdpi.com/2673-4591/158/1/30)). No public benchmark was found for command-acknowledgement round-trips, lost-link detection and recovery, or glass-to-glass video across several vehicles with an open, reproducible harness. The four targets sit two to three orders of magnitude above the autopilot-to-companion hop, so they are decided by the link, QoS choices, buffering and state-machine policy, which is exactly what a harness measures.

| Target | What actually dominates | Evidence | Design consequence |
|---|---|---|---|
| Telemetry ≤100 ms | The link and bridge queuing. DDS on a LAN adds microseconds to milliseconds; LTE adds 33–97 ms on average | [PMC10674650](https://pmc.ncbi.nlm.nih.gov/articles/PMC10674650/); [arXiv 2106.16051](https://arxiv.org/pdf/2106.16051) | Best-effort, keep-last QoS for telemetry; one I/O thread and queue per vehicle; timestamps in every sample. On a single host the target is met trivially, so the harness must inject impairment |
| Command ACK ≤1 s | Retry policy. mavlink.io gives no numeric timeout, and `ACCEPTED` means "will act", not "done" | [mavlink.io Command Protocol](https://mavlink.io/en/services/command.html) | Measure time to the first definitive `COMMAND_ACK`; short per-attempt timeouts that increment `confirmation` (for example about 300 ms × 3, a design choice); a separate long timeout after `IN_PROGRESS`; reliable QoS for commands and ACKs |
| Video ≤300 ms | Capture and jitter buffers. WebRTC adds about 40 ms on a LAN; LL-HLS about 770 ms | [computingforgeeks benchmark](https://computingforgeeks.com/?p=180693) (methodology unverified); [Open Robotics analysis](https://discourse.openrobotics.org/t/where-does-latency-in-webrtc-video-streaming-come-from-an-analysis/54566) | WebRTC/WHEP, never HLS; B-frames off; watch default buffer settings |
| Lost-link recovery ≤5 s | The detection rule (1 Hz heartbeat with 4–5 missed ≈ 4–5 s), the keyframe interval, and DDS reliability over lossy links | [mavlink.io Heartbeat](https://mavlink.io/en/services/heartbeat.html); [arXiv 2407.03091](https://arxiv.org/pdf/2407.03091) | Detect outages from any received message, not heartbeats alone; keyframe interval ≤1 s; re-sync vehicle state on recovery |

The lost-link target deserves the most attention because the conventional rule nearly consumes it. mavlink.io says heartbeats are "typically" sent at 1 Hz on radio links and that a system counts as disconnected when "four or five messages are not received" ([mavlink.io Heartbeat](https://mavlink.io/en/services/heartbeat.html)), so a bridge that follows the convention spends 4–5 s just noticing the outage. Telemetry streams at 10–50 Hz, which lets the bridge declare a link degraded after a gap of a few hundred milliseconds and lost after 1–2 s. That leaves time for the actual recovery work: reconnecting and resuming streams, reapplying message rates if the autopilot rebooted (a decrease in `SYSTEM_TIME.time_boot_ms` signals a reboot, per [mavlink.io Routing](https://mavlink.io/en/guide/routing.html)), and waiting for the next video keyframe, since a lost keyframe can stall video for seconds ([Open Robotics analysis](https://discourse.openrobotics.org/t/where-does-latency-in-webrtc-video-streaming-come-from-an-analysis/54566)). Vehicles also act on their own during an outage. PX4 Offboard mode needs a setpoint stream of at least 2 Hz and fails over after `COM_OF_LOSS_T` ([PX4 Offboard](https://docs.px4.io/main/en/flight_modes/offboard)), and ArduPilot Guided mode stops after 3 s without a velocity command ([ArduPilot Guided commands](https://ardupilot.org/dev/docs/copter-commands-in-guided-mode.html)). Recovery must therefore re-read mode and mission state and never replay stale setpoints. The 50 s Fast DDS outlier is a second warning: **keep DDS off the radio link in version 1**. Run the bridge on the ground side with one MAVLink channel per vehicle, so the radio carries signed MAVLink, which was designed for that hop, and add a companion-side deployment later with Zenoh on the wireless segment.

A credible harness needs five properties. It must impair each vehicle's link separately, because on one host everything passes trivially. It must carry timestamps inside the IDL samples (source time, bridge receive, bridge publish, gateway send and browser render) with clocks disciplined by chrony or PTP. It must run PX4's lockstep SIH simulator at speed factor 1 for repeatability ([PX4 SIH](https://docs.px4.io/main/en/sim_sih/)). It must publish p50, p95 and p99 rather than means, against named impairment profiles. And it should compare DDS implementations and Zenoh under Wi-Fi-like impairment, which the mesh study flags as under-studied. Measuring DDS-Security overhead would also be new, since no drone benchmark of it was found, and Cyclone's bundled `ddsperf` covers microbenchmarks of the DDS layer itself ([cyclonedds ddsperf](https://github.com/eclipse-cyclonedds/cyclonedds/tree/master/src/tools/ddsperf)).

## Cyclone DDS 11.1 holds up, but secure cross-vendor interop is unproven

The planned middleware is defensible. Cyclone DDS and cyclonedds-cxx were both released as **11.1.0 on 9 November 2026**, after 11.0.0 in February and 11.0.1 in March ([Cyclone releases](https://github.com/eclipse-cyclonedds/cyclonedds/releases)), under a dual EPL-2.0 or BSD-style EDL-1.0 licence ([Cyclone LICENSE](https://github.com/eclipse-cyclonedds/cyclonedds/blob/master/LICENSE)). cyclonedds-cxx implements the standard ISO C++ PSM API in C++17, which a C++20 project consumes directly and which belongs to the same API family as RTI's Modern C++ API ([cyclonedds-cxx README](https://github.com/eclipse-cyclonedds/cyclonedds-cxx/blob/master/README.md)). Cyclone 11.0.x is a Tier-1 middleware in ROS 2 Lyrical Luth, the May 2026 LTS release whose Tier-1 platform is Ubuntu 26.04 and whose minimum language level is C++20 ([Lyrical supported platforms](https://github.com/ros2/ros2_documentation/blob/rolling/source/Releases/lyrical/supported-platforms.rst); [Release-Lyrical-Luth](https://github.com/ros2/ros2_documentation/blob/rolling/source/Releases/Release-Lyrical-Luth.rst)). The real concern is maintenance concentration: Cyclone shipped nothing for **about 21 months** between 0.10.5 (May 2024) and 11.0.0, and the 2026 releases, new CI and fuzzing reduce that risk without removing it ([Cyclone 11.1.0 release](https://github.com/eclipse-cyclonedds/cyclonedds/releases/tag/11.1.0)).

| Stack | Current release | Licence | Role for this project |
|---|---|---|---|
| Cyclone DDS + cyclonedds-cxx | 11.1.0 (9 Nov 2026) | EPL-2.0 / EDL-1.0 | Primary |
| Fast DDS | 3.6.2 (2 Jul 2026); 3.6 LTS, end of life May 2031 | Apache-2.0 | Interop peer; default ROS 2 middleware |
| OpenDDS | 3.34.0 (21 May 2026) | Custom permissive | Heavy toolchain (ACE/TAO); more security gaps |

Sources: [Fast DDS RELEASE_SUPPORT](https://github.com/eProsima/Fast-DDS/blob/master/RELEASE_SUPPORT.md); [OpenDDS v3.34.0](https://github.com/OpenDDS/OpenDDS/releases/tag/v3.34.0); [RTI lifecycle](https://community.rti.com/node/6681); [RTI NCL](https://www.rti.com/ncl).

Most interop failures come from data-model defaults, not the wire protocol. Cyclone defaults to **`final` extensibility** while OpenDDS defaults to `appendable` and writes XCDR2, so other vendors "may not match unless configured for XCDR1" ([Cyclone xtypes_relnotes](https://github.com/eclipse-cyclonedds/cyclonedds/blob/master/docs/dev/xtypes_relnotes.md); [OpenDDS XTypes](https://opendds.readthedocs.io/en/latest-release/devguide/xtypes.html)). Cyclone's XTypes notes list maps, bitsets and wide strings as unsupported, though parts of them are stale now that 11.1.0 has added mutable unions and recursive types. That same release **numbers automatic union-case member IDs from 1**, so all bindings must be regenerated together or `idlc` must run with `-f legacy-union-member-ids` ([Cyclone 11.1.0 release](https://github.com/eclipse-cyclonedds/cyclonedds/releases/tag/11.1.0)). Cyclone sends version-2 type information while Connext sends version 1 in a vendor-specific field ([omg-dds/dds-xtypes](https://github.com/omg-dds/dds-xtypes/releases/tag/v2.0.2025-wip)), and Cyclone's shared-memory path accepts only fixed-size types, so strings and sequences disable it ([Cyclone SHM limitations](https://github.com/eclipse-cyclonedds/cyclonedds/blob/master/docs/manual/shared_memory/limitations.rst)). The safe IDL profile follows: annotate every type explicitly, put `@key` on a `uint32 vehicle_id` so that MAVLink's new 32-bit system IDs never force a model break, avoid maps, bitsets, unions and `@optional` in types that face other vendors, pin the XCDR version on writers, and validate against the OMG `shape_main` binaries, whose dds-rtps release v2.1.2026 ships Cyclone 11.0.1, Fast DDS 3.6.1, OpenDDS 3.35-dev and Connext 7.7.0 ([omg-dds/dds-rtps v2.1.2026](https://github.com/omg-dds/dds-rtps/releases/tag/v2.1.2026)). Fast DDS is absent from the separate XTypes interop suite.

Security is the riskiest requirement. On paper the features are broadly equal: Cyclone, Fast DDS and OpenDDS all implement the OMG built-in plugins (PKI-DH authentication, Permissions access control, AES-GCM-GMAC crypto), and Cyclone accepts `pkcs11:` URIs for hardware key storage ([Cyclone plugins config](https://github.com/eclipse-cyclonedds/cyclonedds/blob/master/docs/manual/security/plugins_config.rst); [Cyclone PKCS#11](https://github.com/eclipse-cyclonedds/cyclonedds/blob/master/docs/manual/security/pkcs11_hsm.rst)), while OpenDDS lacks origin authentication, PKCS#11, CRL/OCSP and AES-128 ([OpenDDS DDS Security](https://opendds.readthedocs.io/en/latest-release/devguide/dds_security.html)). In practice, the OMG security interop release of May 2026 ships binaries only for **Connext 7.7 and CoreDX**, and it records that Connext 7.7 "fails to talk to" CoreDX 6.1.0 because Connext 7.4 adopted DDS-Security 1.2 authentication class IDs ([omg-dds/dds-security](https://github.com/omg-dds/dds-security/releases/tag/2026-05-20); [RTI 7.4 What's New](https://community.rti.com/static/documentation/connext-dds/current/doc/manuals/connext_dds_secure/release_notes/whats_new/740/whats_new_740.html)). The only public Cyclone cross-vendor attempt found, a 2023 Connext–Cyclone secure-handshake failure, never received a public root cause ([RTI Community](https://community.rti.com/node/6002)), and Fast DDS patched three CVEs in its access-control parser as recently as July 2026 ([Fast DDS v3.6.2](https://github.com/eProsima/Fast-DDS/releases/tag/v3.6.2)). The project should test secure handshakes against Fast DDS 3.6 and Connext 7.7 (under its non-commercial licence) in its first month. **Publishing that secure-interop matrix is a cheap, credible differentiator**, because nobody else publishes one. The certificate workflow is identical across vendors and works fully offline with OpenSSL: identity and permissions CAs, one certificate per participant, and governance and permissions XML signed as S/MIME, with permissions able to restrict publishing and subscribing per partition ([OpenDDS dds_security.rst](https://github.com/OpenDDS/OpenDDS/blob/master/docs/devguide/dds_security.rst)).

The DDS-layer research supports a QoS profile along the following lines, with one domain per fleet, a partition per vehicle plus a `fleet` partition for broadcast commands, and per-partition permissions. Explicit request and acknowledgement topics are safer than DDS-RPC, whose support parity across vendors (Cyclone's especially) was not established.

| Data | Reliability | History | Durability | Other |
|---|---|---|---|---|
| Telemetry | Best-effort | Keep-last 1–5 | Volatile | Deadline 2–3× the publish period; liveliness lease about 1–2 s |
| Health/status | Reliable | — | Transient-local (late joiners get the last state) | — |
| Command request | Reliable | Keep-all or keep-last N | Volatile | `@key command_id` |
| Command ACK/NAK | Reliable | — | — | `@key command_id`; states such as accepted, in progress, rejected, timed out |

Browsers cannot take part in DDS-Security, so whichever gateway serves the control station is the trust boundary. Zenoh offers one open route: zenoh-bridge-dds embeds Cyclone and builds with DDS-Security on Linux, and the zenoh-ts library connects browsers over WebSocket, all at version 1.10.2. The costs are that the browser must decode raw CDR bytes, zenoh-ts maturity is uncertain, and a Rust daemon joins the stack ([zenoh-plugin-dds](https://github.com/eclipse-zenoh/zenoh-plugin-dds); [zenoh-ts](https://github.com/eclipse-zenoh/zenoh-ts)). For a solo developer, a gateway embedded in the bridge is simpler and keeps command authorisation inside one process. The Foxglove SDK (MIT, v0.31.0, November 2026) supplies a C++ WebSocket server ([foxglove-sdk releases](https://github.com/foxglove/foxglove-sdk/releases); [Foxglove WebSocket server](https://docs.foxglove.dev/docs/sdk/websocket-server)), but its TLS support is unconfirmed and Foxglove's own viewer is no longer open source, leaving the Lichtblick fork as the open debugging client ([ROS Discourse: Foxglove 2.0](https://discourse.openrobotics.org/t/foxglove-2-0-integrated-ui-new-pricing-and-open-source-changes/36583); [Lichtblick](https://lichtblick-suite.github.io/docs)). ROS 2 interop works from plain cyclonedds-cxx if a mirror topic set follows ROS conventions: the `rt/` topic prefix, `pkg::msg::dds_::Type_` type names, `final`/XCDR1 types and the default partition ([ROS 2 topic name mapping](https://design.ros2.org/articles/topic_and_service_names.html)). ROS 2 users on the Tier-1 `rmw_zenoh_cpp` will not see DDS traffic without a bridge.

Recording is where novelty needs careful framing. eProsima DDS Record & Replay (Apache-2.0, v1.5.4) already records any DDS traffic into MCAP ([DDS-Record-Replay releases](https://github.com/eProsima/DDS-Record-Replay/releases)), so DDS recording alone is not new. What is missing is one file holding both the raw MAVLink frames and the DDS samples: MCAP's registry defines `cdr` with `omgidl` schemas but **no MAVLink encoding** ([MCAP registry](https://mcap.dev/spec/registry)). The bridge should embed the MIT-licensed MCAP C++ library (v2.2.0, October 2026) with a custom `mavlink2` channel for raw frames ([foxglove/mcap releases](https://github.com/foxglove/mcap/releases)), and make replay deterministic by giving the protocol state machines an injected clock instead of wall-clock time.

## MAVLink changed under everyone's feet in 2026

Owning the protocol logic in C++20 is the right call, but the parsing should rest on MIT-licensed generated code. The XML definitions and generated C library are MIT, and while the `mavgen` generator is LGPLv3, using it at build time does not make the bridge LGPL ([mavlink.io licence](https://mavlink.io/en/#license)). `c_library_v2` is regenerated from upstream almost daily and includes signing primitives ([mavlink/c_library_v2](https://github.com/mavlink/c_library_v2)), so vendor it at a pinned commit and wrap it in your own C++ types and per-vehicle state machines. libmav (now at Auterion, BSD-3) loads message sets from XML at runtime, which suits switching dialects, but it is pre-1.0 (v0.0.2, April 2026) and changes slowly ([Auterion/libmav](https://github.com/Auterion/libmav)). MAVSDK 4.2.x and pymavlink 2.4.50 serve best as independent test peers ([pymavlink releases](https://github.com/ArduPilot/pymavlink/releases)). Header framing itself is still moving: the generator gained 32-bit system-ID support on 30 October 2026 and QGroundControl implemented it ([pymavlink PR #1295](https://github.com/ArduPilot/pymavlink/pull/1295); [QGC PR #15181](https://github.com/mavlink/qgroundcontrol/pull/15181)), but no flight-stack support was found, so leave extended IDs disabled and keep the IDL key wide.

Signing went from niche to mainstream in 2026, and every implementation behaves differently. PX4 merged signing in March 2026 ([PX4 PR #25284](https://github.com/PX4/PX4-Autopilot/pull/25284)), then **made it spec-compliant as a breaking change in v1.18**: it activates only when a key is present on the SD card, rejects `SETUP_SIGNING` while armed, drops `MAV_SIGN_CFG`, and forces users of v1.17 signing to re-provision keys ([PX4 v1.18 release notes](https://github.com/PX4/PX4-Autopilot/blob/main/docs/en/releases/1.18.md)). MAVSDK v4.2.0 enforces signed-only traffic with no unsigned allow-list (not even `RADIO_STATUS`) and uses link ID 0 for every connection ([MAVSDK PR #3198](https://github.com/mavlink/MAVSDK/pull/3198)). ArduPilot adds per-channel signing through `MAVn_OPTIONS` and states that signing does "NOT encrypt the data" ([ArduPilot MAVLink2 signing](https://ardupilot.org/copter/docs/common-MAVLink2-signing.html)). A 2026 public ICS advisory for CVE-2026-1579 describes unauthenticated `SERIAL_CONTROL` access to PX4 v1.16 when signing is off ([ICSA-26-090-02](https://www.cisa.gov/news-events/ics-advisories/icsa-26-090-02)). The reference implementations carry documented traps: the C library does not check `link_id` when creating a new signing stream ([pymavlink #580](https://github.com/ArduPilot/pymavlink/issues/580)), and until an October 2026 fix, Python recorded the replay timestamp before verifying the signature, so one forged frame could block a stream's genuine traffic ([pymavlink PR #1301](https://github.com/ArduPilot/pymavlink/pull/1301)). The bridge should therefore keep replay state per `(link, sysid, compid)`, commit a timestamp only after verification, hold per-link keys and an explicit unsigned allow-list, forward signed frames byte-for-byte ([mavlink.io Routing](https://mavlink.io/en/guide/routing.html)), and strip `SETUP_SIGNING` and signature blocks before writing any log ([mavlink.io Message Signing](https://mavlink.io/en/guide/message_signing.html)). Confidentiality on IP links needs a separate tunnel such as WireGuard or IPsec, which is a design inference rather than sourced guidance.

Being vendor-agnostic means coding around real behavioural differences. PX4 encodes parameter values bytewise while ArduPilot casts them to float, and neither sets the capability bit that announces it ([mavlink.io Parameter Protocol](https://mavlink.io/en/services/parameter.html)). ArduPilot mission uploads are non-atomic, have no explicit cancel and hold home at sequence 0, so "modify mission" should be modelled as a full re-upload verified by the mission's opaque ID ([mavlink.io Mission Protocol](https://mavlink.io/en/services/mission.html)). ArduPilot 4.7 moved stream rates from `SRx_` to `MAVn_` parameters, and a ground station can silently override rates unless bit 2 of `MAVn_OPTIONS` is set ([ArduPilot: Requesting Data](https://ardupilot.org/dev/docs/mavlink-requesting-data.html)); 4.7.0 also moved the system ID to `MAV_` parameters and removed `HIL_GPS` and `MOUNT_*` ([Copter 4.7.0 thread](https://discuss.ardupilot.org/t/copter-4-7-0-released/144650)). PX4 v1.18 removes dedicated request commands such as `MAV_CMD_GET_HOME_POSITION` in favour of `MAV_CMD_REQUEST_MESSAGE` and reworks RC override ([PX4 v1.18 release notes](https://github.com/PX4/PX4-Autopilot/blob/main/docs/en/releases/1.18.md)), and v1.17 already made MAVLink v1 opt-in only ([PX4 v1.17 release notes](https://docs.px4.io/main/en/releases/1.17)). Because both autopilots default to system ID 1, the bridge must detect duplicate system IDs across channels and refuse them, and should take its own ID from the ground-station range of 245–254 ([mavlink.io Routing](https://mavlink.io/en/guide/routing.html)). The baseline versions are **PX4 v1.17.0** (stable, 13 May 2026) with **v1.18.0-rc2** (17 November 2026) as the next target ([PX4 releases](https://github.com/PX4/PX4-Autopilot/releases)), and **ArduPilot Copter 4.7.x**; GitHub lists Copter-4.7.2 on 14 October 2026, which a late-September forum summary had not yet seen ([ArduPilot releases](https://github.com/ArduPilot/ardupilot/releases)).

## Simulation belongs in Ubuntu 24.04 containers, not on the 26.04 host

The host OS is ahead of the simulation ecosystem. PX4 states that **"Ubuntu 26.04 is not yet supported"**, builds and releases on 24.04, and CI-tests only Gazebo Harmonic ([PX4 Ubuntu dev env](https://docs.px4.io/main/en/dev_setup/dev_env_linux_ubuntu)). Gazebo publishes **only Jetty binaries on Ubuntu 26.04**: Harmonic (LTS until May 2029) has none there, and Ionic reaches **end of life in December 2026** ([Gazebo releases](https://gazebosim.org/docs/latest/releases/); [Gazebo Jetty install](https://gazebosim.org/docs/jetty/getstarted/)). ArduPilot's `ardupilot_gazebo` plugin recommends Harmonic ([ardupilot_gazebo](https://github.com/ArduPilot/ardupilot_gazebo)), its own Docker environment is "not recommended except for special cases", and its prerequisites script refuses operating systems past standard support ([ArduPilot Linux build setup](https://ardupilot.org/dev/docs/building-setup-linux.html)). The host itself is well supported for containers: Docker Engine supports Ubuntu 26.04, and NVIDIA Container Toolkit 1.20.2-1 lists it ([Docker Engine on Ubuntu](https://docs.docker.com/engine/install/ubuntu/); [NVIDIA CTK platforms](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/supported-platforms.html)). The bridge should build natively on 26.04, whose GCC 15 toolchain MAVSDK v4.1 already moved to ([MAVSDK releases](https://github.com/mavlink/MAVSDK/releases)), while PX4 and ArduPilot run in **Ubuntu 24.04 images with Gazebo Harmonic**. Keep the host's Python 3.14 out of the simulation toolchain: the containers carry their own interpreters, and Python KLV tools such as pymisb are CI-tested only on 3.12–3.13 ([PyPI pymisb](https://pypi.org/project/pymisb/)).

Rendering camera sensors on the RTX 3050 takes deliberate configuration. Gazebo renders headlessly through EGL, which works with OGRE2 only (`gz sim -s --headless-rendering`) and requires membership of the `render` group ([Gazebo headless rendering](https://gazebosim.org/api/sim/8/headless_rendering.html)). PX4's container recipe defaults to software rendering, and for NVIDIA it needs `--gpus all` with `NVIDIA_DRIVER_CAPABILITIES` that include `graphics`, because "the default NVIDIA compute/utility capabilities do not include graphics/display libraries" ([PX4 Gazebo container GUI](https://docs.px4.io/main/en/simulation/gazebo_container_gui)). On a hybrid-graphics laptop the host must also run the proprietary driver (an inference), and GUI containers will reportedly go through XWayland because 26.04 drops X11 sessions ([Ubuntu Discourse](https://discourse.ubuntu.com/t/i-need-some-advice-now-that-ubuntu-is-dropping-support-for-x11-in-26-04/77161/2), weakly sourced). No controlled VRAM or RAM figures per drone exist. One forum report had three x500s on Harmonic under 60% CPU and 40% GPU, while a three-drone uXRCE-DDS swarm hit "Accel #0 fail: TIMEOUT", which a maintainer attributed to CPU overload ([PX4 forum: accel timeout](https://discuss.px4.io/t/accel-0-timeout-error-in-swarm-uavs-with-ros2-uxrce-dds-and-gazebo-harmonic/46587)). Four cameras in simple worlds on 4 GB of VRAM and 15 GB of RAM is a hypothesis to measure, with the GUI off by default.

Multi-vehicle mechanics differ by autopilot. A PX4 instance launched with `-i N` gets system ID N+1, an API port of 14540+N and video on UDP 5600+N, and later instances attach to the first one's Gazebo server with `PX4_GZ_STANDALONE=1` ([PX4 multi-vehicle Gazebo](https://docs.px4.io/main/en/sim_gazebo_gz/multi_vehicle_simulation); [PX4 Gazebo SITL](https://docs.px4.io/main/en/sim_gazebo_gz/)). In the official containers MAVLink **listens only on localhost unless `MAV_{i}_BROADCAST=1` is set** ([PX4 pre-built SITL packages](https://docs.px4.io/main/en/simulation/px4_sitl_prebuilt_packages)), and the uXRCE-DDS namespace changed from `px4_N` in v1.17.0 to `uav_N` on main while the docs still show the old form ([px4-rc.uxrce_dds @ main](https://github.com/PX4/PX4-Autopilot/blob/main/ROMFS/px4fmu_common/init.d-posix/px4-rc.uxrce_dds)), so set it explicitly per instance. ArduPilot's `sim_vehicle.py --count N --auto-sysid` gives N endpoints with built-in physics ([ArduPilot Using SITL](https://ardupilot.org/dev/docs/using-sitl-for-ardupilot-testing.html)); its ports step by 10 per instance according to community sources only, and every `GstCameraPlugin` defaults to UDP 5600, so each model copy needs its own port in its SDF ([ardupilot_gazebo](https://github.com/ArduPilot/ardupilot_gazebo)). The sensible tiering is PX4 SIH (`px4io/px4-sitl:<tag>`, about 100 MB, headless, lockstep, no camera) plus ArduPilot's built-in physics for CI and protocol tests ([PX4 SIH](https://docs.px4.io/main/en/sim_sih/)), Gazebo (`px4io/px4-sitl-gazebo:<tag>`, about 2 GB) for video, and speed factor 1 for every latency run.

Fault injection has one gap that shapes the whole harness. PX4's `failure` command (enabled with `SYS_FAILURE_EN`) covers GPS, battery, IMU and motor faults in Gazebo and SIH, but it **rejects `mavlink_signal` and `rc_signal`**, so link loss must be emulated in the network ([PX4 failure injection](https://docs.px4.io/main/en/debug/failure_injection)). ArduPilot SITL offers `SIM_GPS_DISABLE`, `SIM_RC_FAIL`, wind and noise parameters ([ArduPilot SITL parameters](https://ardupilot.org/dev/docs/SITL_simulation_parameters.html)); names for its battery and motor failure parameters were not verified. `tc netem` needs `NET_ADMIN` and shapes only outgoing traffic, so both directions need shaping ([Red Hat: container latency](https://developers.redhat.com/articles/2025/05/26/how-simulate-network-latency-local-containers)), and Pumba wraps netem with correlated loss models ([Pumba network chaos](https://raw.githubusercontent.com/alexei-led/pumba/master/docs/network-chaos.md)). Because Gazebo transport across separate containers is undocumented, the cleanest design (a design inference) keeps the simulator in one container and places a small **link-emulator container per vehicle**, a MAVLink/UDP forwarder with its own netem profile, between the simulator and the bridge. For hardware in the loop, classic PX4 HITL is documented only for Gazebo Classic and "may not work with current PX4 versions", so **SIH running on the flight controller** (`SYS_HITL=2`) is the practical route ([PX4 HITL](https://docs.px4.io/main/en/simulation/hitl)); a Pixhawk 6C Mini costs about US$177 ([Holybro](https://holybro.com/products/pixhawk-6c-mini)), and ArduPilot's Simulation on Hardware needs a custom build except on Cube Orange ([ArduPilot Sim on Hardware](https://ardupilot.org/dev/docs/sim-on-hardware.html)).

## KLV video fits in 300 ms, but muxers fail silently

**MISB ST 0601.19 (2 March 2023)** is the edition that 2026 libraries cite ([lib.rs klv-uas](https://lib.rs/crates/klv-uas)), with the local-set version carried in item 65 ([jMISB ST 0601 docs](https://westridgesystems.github.io/jmisb/org/jmisb/api/klv/st0601/package-summary.html)). Whether a newer edition exists could not be confirmed, because the official registry would not load during research. The useful minimum set is tags 1 (checksum) and 2 (precision timestamp), 5–7 or 90–91 (platform attitude), 13–15 (sensor position), 16–17 (field of view), 18–20 (gimbal angles relative to the platform), 21 (slant range), 23–25 (frame centre), 82–89 (full corners) and 65 (version) ([ImpleoTV ST 0601 tags](https://www.impleotv.com/content/misbcore/help/user-guide/st601-supported.html)). AI detections can later ride in the nested ST 0903 set. Byte-level encodings must be checked against the standard's text, which should be linked rather than vendored because its redistribution terms are unclear.

Open-source KLV support is less empty than it first looks, but it leaves a specific gap. KWIVER (Kitware, BSD) is a full C++ ST 0601 reader and writer with FFmpeg muxing and a `dump-klv` tool, but it is a large framework ([Kitware/kwiver](https://github.com/Kitware/kwiver); [KWIVER KLV arrow](https://kwiver.readthedocs.io/en/latest/_sources/arrows/klv.rst.txt)). jMISB covers Java, Python's klvdata is stale at version 0.0.3 ([klvdata](https://paretech.github.io/klvdata)), Rust's `klv-uas` only parses, and the polished C++ options are commercial ([MisbCore](https://impleotv.com/content/misbcore/help/); [RidgeRun LibMISB](https://developer.ridgerun.com/wiki/index.php/LibMISB)). The real gap is a **small, embeddable, permissively licensed C++20 codec**, with KWIVER's `dump-klv` serving as an independent oracle. Clean public test streams are also missing: one well-known sample is marked "not authorized for public release" ([NIST resources](https://www.nist.gov/itl/iad/image-group/digital-video-exchange-standards-resources)), so openly licensed synthetic streams generated from SITL are a second small contribution.

Carrying KLV through the media path has broken more than once. GStreamer's mpegtsmux needs one KLV buffer per video frame **with a PTS identical to the frame's** ([gstreamer-devel](https://lists.freedesktop.org/archives/gstreamer-devel/2017-September/065605.html)), and it has had version-specific failures where the KLV data stream appears in the program table but carries no data ([GStreamer #2670](https://gitlab.freedesktop.org/gstreamer/gstreamer/-/issues/2670)); GStreamer 1.28.0 (January 2026) now exposes KLV streams in decodebin3 ([GStreamer 1.28 notes](https://gstreamer.freedesktop.org/releases/1.28/)). FFmpeg 6.1 development builds dropped the first five bytes of each KLV packet ([FFmpeg Trac #10828](https://trac.ffmpeg.org/ticket/10828)), and **MP4 cannot carry KLV at all** ([ffmpeg-user](https://ffmpeg.org/pipermail/ffmpeg-user/2021-January/051291.html)). MediaMTX (MIT) gained KLV tracks over RTSP in v1.13, KLV over a WebRTC data channel in v1.16.0 (January 2026) and KLV in MPEG-TS for HLS in v1.17 ([MediaMTX PR #4722](https://github.com/bluenviron/mediamtx/pull/4722); [v1.13.0 notes](https://newreleases.io/project/github/bluenviron/mediamtx/release/v1.13.0); [v1.17.0 notes](https://newreleases.io/project/github/bluenviron/mediamtx/release/v1.17.0)). Its latest release, v1.21.4 (15 November 2026), changed MPEG-TS timestamp rebasing ([MediaMTX releases](https://github.com/bluenviron/mediamtx/releases)), and whether KLV arriving over SRT or MPEG-TS reaches WebRTC readers is unconfirmed. Publish to MediaMTX over **RTSP with a separate KLV track as defined by RFC 6597** ([RFC 6597](https://datatracker.ietf.org/doc/html/rfc6597)), pin media versions, and run an encode-mux-demux-decode round-trip test after every upgrade.

In the browser, WebRTC/WHEP through MediaMTX measured about **40 ms from encoder timestamp to screen on a LAN against about 772 ms for LL-HLS**, though that comes from a single blog benchmark whose methodology could not be verified ([computingforgeeks](https://computingforgeeks.com/?p=180693)). An independent analysis attributes about 100 ms to USB capture, 10 ms or less each to encode and decode, and about 10 ms to WebRTC jitter buffers ([Open Robotics analysis](https://discourse.openrobotics.org/t/where-does-latency-in-webrtc-video-streaming-come-from-an-analysis/54566)), so 60–150 ms end to end is a reasonable SITL estimate. The KLV data channel is not frame-locked, so alignment should key on `rtpTimestamp` or `receiveTime` from `requestVideoFrameCallback`, since `captureTime` is "too unreliable" ([WICG rVFC](https://wicg.github.io/video-rvfc); [WPT test](https://chromium.googlesource.com/external/w3c/web-platform-tests/+/refs/tags/merge_pr_45876/video-rvfc/request-video-frame-callback-webrtc.https.html)), together with a small per-frame SEI carrying the tag-2 timestamp to join the full KLV; vendor documentation warns that WebRTC metadata delivery is not guaranteed ([Dolby frame metadata](https://optiview.dolby.com/docs/millicast/playback/frame-metadata/)). Comparing tag 2 against render time then gives a continuous per-frame latency monitor for free.

PX4's built-in 5600 stream carries no metadata, and its `libGstCameraSystem.so` sometimes fails to load ([PX4 forum](https://discuss.px4.io/t/px4-sitl-with-gazebo-harmonic-error-loading-libgstcamerasystem-so-and-ekf2-missing-data/47829)). Instead, build a per-drone C++ "virtual payload" process that subscribes to Gazebo camera images and to the bridge's DDS telemetry, interpolates telemetry to each frame's time, and pushes frames and KLV into GStreamer `appsrc` elements. Making the DDS bus the single source of truth for KLV is itself a differentiator. The camera footprint should be computed at the sender (tags 82–89) with consistent altitude references, because MISB sensor altitude is MSL while some tools expect height above ground ([Esri community](https://community.esri.com/t5/imagery-and-remote-sensing/incorrect-video-frame-footprint-for-fmv-video/m-p/750041)). For offline maps, MapLibre GL JS 6.x (6.6.0 by August 2026) with Martin 1.15, which carries the 1.14 fixes for two security advisories ([MapLibre newsletter, Aug 2026](https://maplibre.org/news/2026-09-02-maplibre-newsletter-august-2026/)), can serve a regional Protomaps v4 PMTiles extract (the planet is about 120 GB, and OSM attribution is required even offline) ([Protomaps downloads](https://docs.protomaps.com/basemaps/downloads)) plus Mapterhorn terrain ([Protomaps: Mapterhorn](https://protomaps.com/blog/mapterhorn-terrain/)). Avoid bundling Sentinel-2 cloudless imagery, whose 2018–2024 releases are **CC BY-NC-SA** ([EOX](https://eox.at/2025/03/sentinel-2-cloudless-2024/)). CesiumJS 1.147 works offline only with self-supplied terrain and imagery ([Cesium downloads](https://cesium.com/downloads); [Cesium community](https://community.cesium.com/t/cesium-completely-offline-mode/36153)).

## Air-gapped builds are routine once every dependency is vendored

**CMake 4.5.0** (12 November 2026) is current, with presets schema 13 ([CMake releases](https://github.com/Kitware/CMake/releases)). CMake 4.0 removed compatibility with very old policy versions, so aging third-party CMake files may need the `CMAKE_POLICY_VERSION_MINIMUM` escape hatch ([CMake 4.0 notes](https://cmake.org/cmake/help/latest/release/4.0.html)). FetchContent's `FETCHCONTENT_FULLY_DISCONNECTED` "is not an appropriate way to prevent any network access on the first run", so use local `URL` plus `URL_HASH` sources with `FIND_PACKAGE_ARGS`, or a dependency provider ([CMake FetchContent](https://cmake.org/cmake/help/latest/module/FetchContent.html)). vcpkg 2026.10.16 can be made hermetic with a file-based asset mirror and `x-block-origin`, but its binary cache keys on the exact compiler, so any toolchain change triggers rebuilds ([vcpkg asset caching](https://learn.microsoft.com/en-us/vcpkg/users/assetcaching); [vcpkg binary caching](https://learn.microsoft.com/en-us/vcpkg/reference/binarycaching)). Conan 2.34's air-gap commands are experimental, and Conan fails if any configured remote is unreachable ([Conan save/restore](https://docs.conan.io/2/devops/save_restore.html); [Conan FAQ](https://docs.conan.io/2/knowledge/faq.html)). The simplest robust setup takes GStreamer from the distribution, vendors pinned tarballs of everything else, encodes the offline options in a CMake preset, and proves the air-gap claim by building inside `--network=none` in CI. For the gateway's WebSocket server, Boost.Beast (BSL-1.0, TLS through Asio), IXWebSocket 12.1.0 (BSD-3) and uWebSockets 20.81.0 are all maintained, whereas **websocketpp has not released since 2020** ([websocketpp](https://github.com/zaphoyd/websocketpp); [IXWebSocket](https://github.com/machinezone/IXWebSocket)).

Testing can borrow proven patterns. GoogleTest 1.18.0, Catch2 3.16.1 and doctest 2.5.3 are all current ([googletest releases](https://github.com/google/googletest/releases)). MAVSDK's libFuzzer target builds its list of valid message IDs through `mavlink_get_msg_entry()` so fuzzed frames reach real decoders, which makes it a ready template ([MAVSDK mavlink_fuzzer.cpp](https://github.com/mavlink/MAVSDK/blob/main/cpp/src/fuzz_tests/mavlink_fuzzer.cpp)), and PX4 runs SIH plus MAVSDK integration tests headless in containers ([PX4 sitl_tests.yml](https://github.com/PX4/PX4-Autopilot/blob/main/.github/workflows/sitl_tests.yml)). The frame parser and signature verifier should be fuzzed under AddressSanitizer and UndefinedBehaviorSanitizer with a corpus seeded from recorded tlogs, and the per-vehicle I/O layer should run under ThreadSanitizer. For packaging, `docker image save --platform` moves images to an offline host ([Docker image save](https://docs.docker.com/reference/cli/docker/image/save/)), and PX4 publishes versioned SITL `.deb` packages and images for Ubuntu 22.04 and 24.04 only ([PX4 pre-built SITL](https://docs.px4.io/main/en/simulation/px4_sitl_prebuilt_packages)). Syft 1.57.2 produces CycloneDX and SPDX SBOMs locally ([Syft releases](https://github.com/anchore/syft/releases)), with PX4 v1.18 now generating an SPDX SBOM for every firmware build as a useful precedent ([PX4 v1.18 notes](https://github.com/PX4/PX4-Autopilot/blob/main/docs/en/releases/1.18.md)). cosign 3.1.4 moved to signing-config workflows and deprecated `--tlog-upload=false` on its default path, so fully offline keyed signing needs the exact logless flags for the installed version, the still-patched 2.6.x line, or minisign/GPG ([cosign releases](https://github.com/sigstore/cosign/releases); [Sigstore: Cosign v3](https://blog.sigstore.dev/cosign-3-0-available/)). Check the licence of any video-encoder plugin shipped inside images, since software H.264 encoders are commonly GPL, which matters for a permissively licensed bundle.

## Conclusion: recommended stack and differentiators

The project's real product is a **contract**: the IDL, the QoS and security profiles, and the benchmark method. The bridge, web station and KLV encoder are reference implementations of that contract, and framed that way the project does not compete with QGroundControl, ADOS or MAVROS but becomes the measurable, secure, vendor-neutral data plane they all lack. The timing is unusually good, because signing only just landed in PX4 and MAVSDK, ArduPilot's multi-vehicle DDS support is months old, and ROS 2 Lyrical now targets Ubuntu 26.04 with C++20. The same churn makes pinning and published compatibility matrices more valuable than usual, since PX4 v1.18 final will land mid-project. A sensible build order is the MAVLink core and IDL against four PX4 SIH and four ArduPilot SITL instances first, then signing and DDS-Security with the secure-interop matrix, then the impairment harness, then the web gateway and station, then video and KLV, and finally offline packaging.

| Layer | Recommendation (Nov 2026) | Pitfall to design around |
|---|---|---|
| Toolchain | C++20, GCC 15 natively on Ubuntu 26.04, CMake 4.5 presets, Ninja | CMake 4 drops old policy compatibility; prove offline builds with `--network=none` |
| MAVLink | `c_library_v2` (MIT) pinned to a commit; own C++20 state machines per vehicle and microservice; MAVSDK 4.2.x and pymavlink 2.4.50 as test peers | Per-autopilot quirks (parameter encoding, non-atomic ArduPilot missions, 4.7 renames, v1.18 removed commands); leave 32-bit IDs off |
| Signing | Per-link keys, explicit unsigned allow-list, replay state per `(link,sys,comp)`, persisted timestamps | PX4 v1.18 re-provisioning; strip `SETUP_SIGNING` from logs; signing is not encryption |
| DDS | Cyclone DDS + cyclonedds-cxx 11.1.0 with security enabled; `@appendable` types; `@key uint32 vehicle_id`; pinned XCDR version | Default `final` extensibility; changed union IDs; no maps or bitsets; keep separate from ROS Lyrical's Cyclone 11.0.x install |
| Interop peers | Fast DDS 3.6.2 LTS, OMG `shape_main` (dds-rtps v2.1.2026), Connext 7.7 under its non-commercial licence | No public Cyclone secure-interop evidence; DDS-Security 1.2 class-ID drift |
| Security | Offline OpenSSL CA; governance encrypting discovery and data; permissions per partition; WireGuard on IP links | Browser sits outside DDS-Security, so the gateway enforces command authorisation |
